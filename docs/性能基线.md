# OutboxPro Relay 性能基线（V1.4）

> 测量日期：2026-11-07  
> 适用版本：1.4.0  
> 目的：给出同一台机器上可复现的相对基线，用于选择 `producer.workers` 与
> `producer.batch-size`，并作为后续版本回归对比的锚点。

## 1. 结论

在 2000 条 PENDING 记录、真实 MySQL 8.4、零延迟 Publisher（不经过 RabbitMQ 网络）的条件下：

| 配置 | 耗时 | 吞吐 |
|---|---:|---:|
| workers=1，batch=100 | 2430 ms | 823 records/s |
| workers=1，batch=500 | 2085 ms | 959 records/s |
| workers=2，batch=500 | 1049 ms | 1907 records/s |
| workers=4，batch=500 | 717 ms | 2789 records/s |

观察：

- batch 从 100 提升到 500，单 worker 吞吐提升约 17%，主要来自减少认领 SQL 轮次；
- workers 从 1 提升到 2，吞吐接近翻倍（约 2.0×）；
- workers 从 2 提升到 4，吞吐继续提升约 46%，说明在连接池充足时认领并发仍有效；
- 生产建议从 `workers=2–4`、`batch-size=100–500` 起步，并按数据库连接池
  （至少 `workers + 1` 个连接）和 Broker Confirm 吞吐调整。

以上数字**不包含 RabbitMQ 网络往返与 Confirm 等待**，不能直接当作生产端到端吞吐；
真实吞吐还受 Broker、网络 RTT、消息大小和数据库规格约束。

## 2. 测试环境

| 项 | 值 |
|---|---|
| 操作系统 | Linux 7.0.0-43-generic |
| JDK | 21.0.12 |
| 数据库 | Testcontainers `mysql:8.4`，单实例 |
| 连接池 | HikariCP，`maximum-pool-size=8`（性能测试通过系统属性放大） |
| 记录数 | 2000 条 PENDING |
| 发布实现 | `NoopPublisher`（同步返回 Confirm 成功，零网络延迟） |
| 租约 | `claim-timeout=30s` |
| 运行方式 | 单 JVM，Relay 工作线程为普通线程池 |

## 3. 测试方法

测试类：`outboxpro-spring-boot-autoconfigure/src/test/java/org/outboxpro/integration/OutboxRelayThroughputTest.java`。

1. 清空 Outbox 表，用 JDBC batch 预插入 2000 条 PENDING 记录；
2. 使用生产同款 `OutboxRelayScheduler`：单个 `OutboxRelay` + N 个 worker，
   `poll-interval=1ms`、`idle-backoff-max=5ms`，确保测到的是实际发布路径
   （共享 Relay、租约恢复节流、多线程认领），而不是测试自建的线程池；
3. 主线程轮询 `COUNT(status='SENT')`，达到 2000 时停止计时并 `stop()` 调度器；
4. 用 `System.nanoTime()` 计算墙钟耗时，吞吐 = 记录数 / 耗时；
5. 测试结束强校验全部记录为 SENT，并设置 60 秒排空上限，避免调度器吞掉异常时
   测试永久挂起。

运行命令：

```bash
mvn -B -pl outboxpro-spring-boot-autoconfigure -am test \
  -Dtest=OutboxRelayThroughputTest \
  -Doutboxpro.performance=true \
  -Dsurefire.failIfNoSpecifiedTests=false
```

该测试带 `@Tag("performance")` 且默认跳过，不会进入常规 CI。

## 4. 历史数据与一次真实退化

同一测试在 V1.4 开发早期（未做租约恢复节流、未显式使用 READ_COMMITTED，
且使用独立 Relay + 默认 3 连接池）的结果：

| 配置 | 吞吐 |
|---|---:|
| workers=1，batch=500 | 917–1023 records/s |
| workers=2，batch=500 | 1871 records/s |
| workers=4，batch=500 | **67 records/s** |

4 worker 耗时约 30 秒，几乎正好等于 `claim-timeout=30s`。根因不是 CPU 或连接池，
而是每个 worker 每轮都执行：

```sql
UPDATE outboxpro_outbox
SET status = 'PENDING', ...
WHERE status = 'PROCESSING' AND claimed_time < ?
```

MySQL 默认 REPEATABLE READ 会为该范围更新加间隙锁，与并发的认领 UPDATE
互相阻塞；被阻塞的批次最终只能等租约过期后由其他 worker 恢复，于是出现
“吞吐骤降 + 耗时约等于租约时长”的特征。

修复包含两层：

1. **恢复节流**：同一 Relay 实例每半个租约周期最多执行一次过期认领恢复
   （最少 1 秒一次），不再每轮扫描；
2. **隔离级别**：`claimBatch` 与 `recoverExpiredClaims` 显式使用
   `READ_COMMITTED`，`FOR UPDATE SKIP LOCKED` 只锁命中行，不持有间隙锁。

修复后同一测试装置恢复到 2232 records/s；改用生产同款调度器并把连接池放大到 8 后，
4 worker 为 2789 records/s（见第 1 节）。该回归由
`OutboxRelayTest.expiredClaimRecoveryIsThrottledBetweenCycles` 锁定。

## 5. 解读与调优建议

- **先看数据库连接池**：`workers` 增大后，每个 worker 至少要能拿到一个连接；
  连接池过小会把并行认领重新串行化。
- **batch 不是越大越好**：批次越大，认领事务持锁时间越长；超过 1000 后收益递减，
  且会增加单次 Confirm 等待的尾延迟。默认 100，吞吐优先可试 500。
- **多实例与多 worker 等效但不同**：多实例天然分摊连接与 CPU；单实例多 worker
  更适合容器 CPU 配额明确的场景。两者都依赖 `SKIP LOCKED`，可以混用。
- **空闲退避**：低流量时 `idle-backoff-max` 把空轮轮询从每秒一次降到每 5 秒一次。
  持续有消息时第一轮就会恢复到 `poll-interval`；但系统完全空闲后到达的第一条消息，
  最坏要等一个 `idle-backoff-max`（默认 5 秒）才被认领。延迟敏感业务应降低该值，
  或设为与 `poll-interval` 相同以关闭退避。
- **端到端压测仍需真实 Broker**：需要评估 RabbitMQ Confirm 吞吐时，应把
  `NoopPublisher` 替换为真实 `RabbitMessagePublisher`，并观察
  `outboxpro.publish.duration`、`outboxpro.publish.confirm.timeout` 与
  `outboxpro.relay.cycle.duration`。

## 6. 复现注意事项

- 必须在同一台机器、同一容器规格下比较；容器冷启动和镜像拉取不计入测试耗时。
- 测试会清空 `outbox_it_throughput` 库的 Outbox 表，仅用于隔离测试环境。
- 结果受 JIT 预热影响；首次运行通常略慢，建议连续运行 2–3 次取稳定值。
- 若看到吞吐接近 `records / claim-timeout`，优先检查是否存在锁等待或 worker
  线程异常，而不是先调大连接池。
