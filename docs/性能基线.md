# OutboxPro Relay 性能基线（V1.4）

> 适用版本：1.4.0。本文只保留容量结论与调优建议；测试环境、复现步骤、历史数据由维护者单独记录。

## 1. 结论

在 2000 条 PENDING 记录、真实 MySQL 8.4、零延迟 Publisher（不经过 RabbitMQ 网络）的条件下：

| 配置 | 耗时 | 吞吐 |
|---|---:|---:|
| workers=1，batch=100 | 2430 ms | 823 records/s |
| workers=1，batch=500 | 2085 ms | 959 records/s |
| workers=2，batch=500 | 1049 ms | 1907 records/s |
| workers=4，batch=500 | 717 ms | 2789 records/s |

观察：

- batch 从 100 提升到 500，单 worker 吞吐提升约 17%，主要来自减少认领 SQL 轮次；
- workers 从 1 提升到 2，吞吐接近翻倍；
- workers 从 2 提升到 4，吞吐继续提升约 46%，说明连接池充足时认领并发仍有效；
- 生产建议从 `workers=2–4`、`batch-size=100–500` 起步，并按连接池（至少 `workers + 1`）和 Broker Confirm 吞吐调整。

> 以上数字**不包含 RabbitMQ 网络往返与 Confirm 等待**，不能直接当作生产端到端吞吐。
> 真实吞吐还受 Broker、网络 RTT、消息大小和数据库规格约束。

## 2. 如何选择配置

- **先看数据库连接池**：`workers` 增大后，每个 worker 至少要能拿到一个连接；连接池过小会把并行认领重新串行化。
- **batch 不是越大越好**：批次越大，认领事务持锁时间越长；超过 1000 后收益递减，并会增加单次 Confirm 等待的尾延迟。
- **多实例与多 worker 等效但不同**：多实例天然分摊连接与 CPU；单实例多 worker 更适合容器 CPU 配额明确的场景。两者都依赖 `SKIP LOCKED`，可以混用。
- **空闲退避**：低流量时 `idle-backoff-max` 把空轮轮询从每秒一次降到每 5 秒一次。系统完全空闲后到达的第一条消息，最坏要等一个 `idle-backoff-max`（默认 5 秒）才被认领；延迟敏感业务应降低该值，或设为与 `poll-interval` 相同以关闭退避。
- **端到端压测仍需真实 Broker**：评估 RabbitMQ Confirm 吞吐时，应观察 `outboxpro.publish.duration`、`outboxpro.publish.confirm.timeout` 与 `outboxpro.relay.cycle.duration`。

## 3. 异常信号

若吞吐接近 `records / claim-timeout`，通常不是 CPU 或连接池不足，而是存在锁等待或 worker 线程异常；应优先检查数据库锁等待与 Relay 日志，而不是继续加线程。
